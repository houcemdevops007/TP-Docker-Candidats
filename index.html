Chapitre 1

Chapitre 1 — Introduction à Docker

Les notions indispensables pour comprendre ce que fait réellement chaque instruction d'un Dockerfile.

30 min Lecture + questions

1.1 Image et conteneur

Une image est un modèle immuable : un empilement de couches de système de fichiers en lecture seule, accompagné de métadonnées (commande de démarrage, variables d'environnement, utilisateur, ports documentés…). Un conteneur est une instance en cours d'exécution d'une image : Docker ajoute au-dessus des couches de l'image une couche inscriptible propre au conteneur, et lance un processus isolé (namespaces, cgroups).

Image
  • Immuable, identifiée par un digest SHA-256
  • Nommée dépôt:tag (ex. tp-docker/java:jar)
  • Partageable via un registre (docker push / pull)
Conteneur
  • Éphémère : ses modifications disparaissent avec lui (sauf volumes)
  • Exécute un processus principal (PID 1)
  • S'arrête quand ce processus se termine

1.2 Le Dockerfile

Un Dockerfile est un fichier texte décrivant, instruction par instruction, comment construire une image. Voici les instructions étudiées dans ce TP :

InstructionRôleCrée une couche ?
FROMImage de base (début d'un stage) ; FROM … AS nom nomme le stageCouches de l'image de base
WORKDIRRépertoire de travail des instructions suivantes (créé si absent)Non significative
COPYCopie des fichiers du contexte de build (ou d'un autre stage avec --from)Oui
ADDComme COPY, plus extraction d'archives locales et téléchargement d'URLOui
RUNExécute une commande au moment du buildOui
CMDCommande (ou arguments) par défaut au démarrage du conteneurNon (métadonnée)
ENTRYPOINTExécutable principal du conteneurNon (métadonnée)
EXPOSEDocumente le port écouté (ne publie rien)Non (métadonnée)
ENVVariable d'environnement présente au build et à l'exécutionNon (métadonnée)
ARGVariable disponible uniquement pendant le build (--build-arg)Non
USERUtilisateur (et groupe) des instructions suivantes et du conteneurNon (métadonnée)
HEALTHCHECKCommande de vérification périodique de l'état de santéNon (métadonnée)
LABELMétadonnées descriptives (auteur, version, licence…)Non (métadonnée)
Forme exec ou forme shell ? CMD ["node", "server.js"] (forme exec, tableau JSON) lance directement le processus. CMD node server.js (forme shell) le lance via /bin/sh -c. Cette différence a des conséquences sur la réception des signaux d'arrêt : vous devrez l'expliquer dans les exercices.

1.3 Docker Engine et BuildKit

Le client docker envoie des requêtes à l'API du démon dockerd, qui délègue l'exécution des conteneurs à containerd puis à runc. Les constructions d'images sont réalisées par BuildKit, le moteur de build par défaut depuis Docker Engine 23 : exécution parallèle des stages, cache avancé, montages de cache (RUN --mount=type=cache), secrets de build, builds multi-plateformes (docker buildx).

1.4 Docker Hub et registres

Un registre stocke et distribue les images. Docker Hub héberge les images officielles (python, node, golang, maven, eclipse-temurin…), maintenues et reconstruites régulièrement. En entreprise, on utilise aussi des registres privés (Harbor, GitLab Registry, Nexus, ECR, ACR, GHCR). Une référence complète d'image s'écrit registre/dépôt:tag@sha256:digest.

Le tag latest n'est pas une version C'est simplement le tag par défaut : son contenu change dans le temps. Dans ce TP, toutes les images de base ont un tag explicite (ex. python:3.14-slim). En production, on épingle même le digest.

1.5 Couches et cache de construction

Chaque instruction RUN, COPY ou ADD produit une couche. Lors d'un nouveau build, Docker réutilise une couche du cache si l'instruction et ses entrées (fichiers copiés, couche parente) sont identiques. Dès qu'une couche change, toutes les couches suivantes sont reconstruites.

BashInspecter les couches d'une image
docker image history python:3.14-slim
docker image inspect python:3.14-slim --format '{{json .RootFS.Layers}}'

1.6 Contexte de build et .dockerignore

Le dernier argument de docker build (souvent .) désigne le contexte de build : l'ensemble des fichiers envoyés au moteur de build et accessibles aux instructions COPY/ADD. Le fichier .dockerignore, placé à la racine du contexte, exclut des fichiers de ce contexte : builds plus rapides, images plus petites, et surtout aucun fichier sensible (.env, clés, .git) embarqué par erreur.

BashSyntaxe d'un build
#            Dockerfile utilisé       nom:tag de l'image       contexte
docker build -f Dockerfile.simple     -t tp-docker/demo:1.0    .

1.7 Multi-stage build

Un Dockerfile peut contenir plusieurs instructions FROM : chacune démarre un stage. Les stages intermédiaires servent à compiler ou préparer ; seul le dernier stage constitue l'image finale, dans laquelle on ne copie (COPY --from=…) que les artefacts nécessaires.
